2. THÔNG TIN REPOSITORY & QUY TRÌNH LÀM VIỆC NHÓM (FORK + PULL REQUEST)
--------------------------------------------------------------------------------
- Repo gốc (upstream): https://github.com/ruicosta-bk/limit-order-book.git
- Trạng thái hiện tại: Đã có commit nền Phase 0 trên nhánh `main` (cấu trúc thư mục,
  CMakeLists.txt, khung test, GitHub Actions CI, .gitignore, CONTRIBUTING.md).

Vai trò trên Git:
- Thành viên 1 (Chủ repo `ruicosta-bk`): Tạo nhánh `feat/...` trên `origin` -> mở PR vào `main`.
- Thành viên 2 (Fork): Fork repo gốc -> clone bản Fork -> gắn `upstream` -> mở PR vào repo gốc.

Quy trình cho Thành viên 2 (Fork):
  Bước 1: Bấm nút "Fork" trên trang repo gốc về tài khoản GitHub cá nhân.
  Bước 2: Clone bản Fork về máy và gắn remote `upstream`:
          git clone https://github.com/<username>/limit-order-book.git
          cd limit-order-book
          git remote add upstream https://github.com/ruicosta-bk/limit-order-book.git
  Bước 3: Trước mỗi đầu việc, đồng bộ nhánh `main` từ `upstream`:
          git checkout main
          git fetch upstream
          git merge upstream/main
          git push origin main
  Bước 4: Tạo nhánh riêng cho từng đầu việc (TUYỆT ĐỐI KHÔNG code trực tiếp trên `main`):
          git checkout -b feat/<tên-tính-năng>
  Bước 5: Build và chạy toàn bộ test pass 100% trên máy:
          cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug
          cmake --build build
          ctest --test-dir build --output-on-failure
          (Nếu không có Ninja thì bỏ cờ `-G Ninja`)
  Bước 6: Commit theo Conventional Commits (`feat:`, `fix:`, `test:`, `refactor:`, `docs:`),
          push nhánh lên Fork và mở Pull Request vào `ruicosta-bk/limit-order-book:main`.

Nguyên tắc CHỐNG XUNG ĐỘT (MERGE CONFLICT):
  1) Không bao giờ để 2 người sửa cùng một vùng khai báo trong `OrderBook.h` cùng lúc.
     Ở Phase có thay đổi cấu trúc dữ liệu (Phase 1, 3, 4), PR sửa Header sẽ MERGE TRƯỚC;
     người còn lại chạy `git fetch/merge` lấy `main` mới nhất rồi làm PR kế tiếp.
  2) Luôn đảo vai giữa "Core Engine" và "Test / Invariants / Interface" qua từng Phase
     để cả hai người đều được tự tay code thuật toán lõi lẫn kiểm thử (tổng 12 PR = 6 PR/người).
  3) Mỗi PR đều do người còn lại review theo Checklist 4 tiêu chí trước khi merge.

Checklist Review chéo bắt buộc trước khi Merge PR:
  [ ] CI trên GitHub Actions build xanh, 0 compiler warning (-Wall -Wextra -Wpedantic),
      pass 100% test.
  [ ] Độ phức tạp thời gian/bộ nhớ đúng thiết kế (không vô tình rớt xuống O(N)).
  [ ] An toàn bộ nhớ C++ (không Dangling Reference sau erase, không Iterator Invalidation,
      không quên xóa trong unordered_map).
  [ ] Đã bao phủ edge cases (quantity == 0, sổ rỗng, khớp sạch tầng giá, trùng OrderId).

4. HIỆN TRẠNG CODE CẦN SỬA NGAY Ở PHASE 1 (5 ĐIỂM KỸ THUẬT)
--------------------------------------------------------------------------------
1) Hàm `matchOrder()` đang viết trực tiếp trong OrderBook.h -> phải tách sang OrderBook.cpp
   để giữ đúng kiến trúc Header/Source (hiện tại compiler báo warning lặp lại ở mỗi file
   include OrderBook.h).
2) Lệch API `getBestBid`/`getBestAsk`: comment hướng dẫn dùng `std::optional<Price>` (C++17)
   nhưng code đang viết `bool getBestBid(Price &outPrice) const;` và thiếu `#include <optional>`.
3) Thiếu `struct Trade` (Execution Report) trả về từ quá trình khớp lệnh; hai biến
   `bestAskPrice`/`bestBuyPrice` đang dư sinh cảnh báo `-Wunused-variable`.
   Nguyên tắc: Engine không in `std::cout` trong hàm khớp mà trả về `std::vector<Trade>`.
4) Nhánh Buy và Sell trong `matchOrder()` bị trùng lặp logic ~95% -> dễ phát sinh bug lệch
   trạng thái khi sang Phase 3 (Hash Map).
5) OrderBook.cpp và main.cpp mới có khung comment, chưa có code cài đặt; chưa chặn edge cases
   (`quantity == 0`, trùng `OrderId`).

[PHASE 1] Chuẩn hóa Thiết kế Core & Hệ Bất biến (Invariants)
* Kiến thức bản chất & C++ cần nắm:
  - Fixed-point integer (`uint64_t` ticks) vs `double` (tránh sai số IEEE 754).
  - `std::optional<T>`, `std::nullopt` (C++17), `const`-correctness, tách `.h` / `.cpp`.
  - 4 Bất biến toán học của Order Book (`checkInvariants()`):
    (1) Best Bid < Best Ask (No Crossed Book)
    (2) Không có LimitLevel rỗng trong bids_/asks_
    (3) totalVolume == tổng remainingQuantity và mọi lệnh có remainingQuantity > 0
    (4) (Từ Phase 3) orderIndex_ khớp 1-1 với tập lệnh trên sổ.

[PHASE 3] Hủy lệnh O(1) (`Cancel Order`) & Sửa lệnh (`Modify / Cancel-Replace`)
* Kiến thức bản chất & C++ cần nắm:
  - Iterator Stability: Vì sao `std::list` giữ iterator ổn định còn `std::vector` thì không.
  - `std::unordered_map<OrderId, OrderLocation>` và độ phức tạp thực tế:
    O(1) hủy giữa hàng đợi, O(log M) hoặc O(1) amortized khi xóa mức giá rỗng khỏi `std::map`.
  - Đồng bộ 2 chiều: Phải xóa khỏi `orderIndex_` ở CẢ `cancelOrder` LẪN khi khớp hết trong `matchOrder`.
  - Luật ưu tiên thời gian khi `Modify`: giảm qty giữ nguyên FIFO; tăng qty/đổi giá mất FIFO.
